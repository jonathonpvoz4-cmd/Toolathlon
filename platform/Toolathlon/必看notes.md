## 如何处理超长上下文
超长上下文处理流程全景
这个系统对超长上下文有两条处理路径：一条是模型真正报错后的「被动强制重置」，一条是 agent 主动调用工具的「主动截断」。核心不是「达到某个 token 阈值就触发」，而是由 LLM API 实际返回的报错来触发（被动），加上 agent 自己判断使用率后主动清理（主动）。

关键点：触发条件不是本地预估 token，而是 API 报错
超长的判定发生在 model_provider.py:846-983（Chat Completions）和 model_provider.py:1028-1087（Responses）的 get_response 重试循环里。它不预先计算 token，而是把请求发出去，捕获异常后用关键字/正则去匹配 API 返回的报错文本：

匹配 Error code: 400 + 一堆关键词（'maximum context length'、'context_length_exceeded'、'prompt is too long'、"exceeds the model's context window" 等，见 L856-872），并用正则从报错里抽出 current_tokens / max_tokens（L877-912）。
一旦判定为超长，不重试，直接抛出自定义异常 ContextTooLongError（L979、L1083），异常上带着 token_count 和 max_tokens。
所以严格回答「超出多少 token 触发」：没有一个本地阈值去主动触发重置。真正的硬触发是 provider（OpenRouter/xAI/kimi 等）在服务端因为超过 context_window 返回 400，这个报错被翻译成 ContextTooLongError。本地记录的 _context_limit（来自 get_context_window，各模型 128k~2M 不等）只用来给 agent 展示使用率百分比，不作硬触发用。

路径 A：被动强制重置（context reset）
ContextManagedRunner._run_single_turn 调 _get_new_response，若抛 ContextTooLongError，在 context_managed_runner.py:364-375 捕获，往 ctx["_force_reset_context"] 里记下已执行的步数，然后重新抛出给上层。

回到 task_agent.py:750-823 的 run_interaction_loop 内层循环 except ContextTooLongError，处理是：

累加已用 inner steps；若 inner steps 用尽则 RuntimeError 硬失败（L763-769）。
调 _reset_context_and_history()（L206-261）：清空 self.logs，但保留 session_id/history_dir/统计/截断历史等 meta，并在 truncation_history 里记一条 force_reset_context。
若是 stateful responses provider，还 server_conversation_tracker.reset()（L777-779）清掉服务端会话链。
从磁盘 jsonl 历史里取最近 10 轮摘要 get_recent_turns_summary（L782-786）。
拼一条新的 user 消息：[Context reset] ... + 原始任务 first_user_input + 最近历史摘要，把 self.logs 重置成只含这一条（L805-808），提示 agent 用 history 搜索工具找细节。
continue 回内层循环，用压缩后的上下文重新推理。
完整历史并没丢——它一直被 _save_items_to_history 逐条落盘到 {session_id}_history.jsonl（L666-693），reset 只是清掉喂给模型的 in-context 部分。

路径 B：主动截断（agent 自己调工具）
Agent 可以用 context_management_tools.py 里的工具主动管理：

local-check_context_status：算 total_tokens / context_limit 的百分比，≥70/80/90% 给出 info/warning/critical 建议（L65-90）。
local-manage_context：按 keep_recent_turns / keep_recent_percent / delete_first_turns / delete_first_percent 策略，设置 ctx["_pending_truncate"]（L168）。
local-smart_context_truncate：按精确 range 保留，设 method="smart_ranges"。
这些工具只打标记，真正执行在 _run_single_turn 尾部检查 _pending_truncate 时调 _handle_truncation（context_managed_runner.py:422-431 → L450-552），依据 boundary_in_current_sequence 轮次边界把 original_input/pre_step_items/new_step_items 三段列表按轮删除，并可保留第一条 user 输入（原始任务）。

总结一张流程图

LLM 请求 ──► provider 服务端超 context_window ──► 返回 400
   └► get_response 关键字/正则匹配 ──► raise ContextTooLongError(token_count, max_tokens)
         └► _run_single_turn 记录 _force_reset_context 并重抛
               └► run_interaction_loop 内层 except:
                     ├─ inner steps 用尽 → RuntimeError（硬失败）
                     └─ 否则 → _reset_context_and_history()（清 logs、留 meta）
                              + 最近10轮摘要 + 原始任务 → 新 user 消息 → continue

并行：agent 主动 check_context_status（看百分比）→ manage_context/smart_truncate
      → 设 _pending_truncate → _handle_truncation 按轮次边界删除历史
一句话：不是「本地估到多少 token 就截断」，而是发出去被 API 拒（超模型 context_window）→ 抛 ContextTooLongError → 清空 in-context logs 并用「原始任务+最近10轮摘要」重启对话；同时 agent 可根据使用率百分比主动按轮次截断作为预防。
